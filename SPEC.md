# SPEC — AI Scientist (Ralphthon Track 1)

You are an autonomous research agent. Your mission: produce a small, real, fully verifiable

## Topic (locked 2026-07-04, Matthew's own question; feasibility spike passed — determinism,
## speed, and capability verified on the event laptop)

**Does more context degrade model performance? If so, when does it start, and by how much?**
Measuring how the AMOUNT, POSITION, and QUALITY
of context change a small language model's accuracy — on experiments anyone can re-run on
a laptop. The subject under test: Qwen2.5-0.5B-Instruct (frozen, checksummed weights in
data/models/), run fully offline and deterministically via llama-completion.

Research questions:
- RQ1 (amount): How does retrieval accuracy change as context grows (~2k → 8k tokens)?
- RQ2 (position): Does WHERE the key fact sits (start / middle / end) change accuracy —
  does the known "lost in the middle" effect of large API models appear in a small
  open model?
- RQ3 (quality — the novel axis): Does RELEVANT-but-redundant extra context hurt less
  than IRRELEVANT filler, or does even "good" context eventually degrade accuracy?
- RQ4 (mitigation): Of the cheap deterministic fixes — placing the key fact first/last,
  pruning context by simple keyword overlap — which recovers the most accuracy?

Claims are DESCRIPTIVE of the tested model — never generalize to "all LLMs". Known caveats
to handle honestly: one small quantized model; synthetic haystack tasks (literal and
paraphrase probes, not natural documents); accuracy on retrieval-style questions is not
general capability; CPU probe budget caps the grid size.

**Experiment design constraints (measured 2026-07-04, 8GB arm64 laptop):**
- Probe costs MEASURED at TRUE tokenizer-verified sizes (2026-07-07, this laptop):
  ~14s at 2k, ~25s at 4k, ~76s at 8k. The FULL probe set must regenerate in ≤ 45
  minutes — do this arithmetic BEFORE running any grid. The pattern that fits: full
  resolution at 2k/4k, a SPARSE top tier (~12 probes at 8k), cheap variants
  (closed-book, pruned) at small tiers only. Do not buy an expensive tier the smaller
  tiers have already answered: if accuracy has floored by 4k, an 8k tier confirms it
  at premium prices.
- SIZE BY THE REAL TOKENIZER from the FIRST lap: never size or label context tiers
  by a chars-per-token estimate — rehearsal lost two inference batches to tiers
  labeled 2k/8k that measured 565/2073 real tokens. Verify prompt sizes with
  llama-tokenize (instant, no model inference) BEFORE running a grid; measured token
  means become the tier labels and the macros. Estimates may seed the generator;
  measurements decide the labels.
- Determinism is a hard rule: --temp 0, fixed --seed, greedy decoding, no sampling.
  Same probes, same model, same numbers — this is what makes the paper verifiable.
- Haystacks/probes are generated by seeded code in analysis/ (synthetic, reproducible).
  Design probes so literal keyword match is NOT always enough (see NoLiMa exemplar) —
  include paraphrase probes, and distractor facts that nearly match. Pilot-verified
  (2026-07-04): literal probes saturate; paraphrase probes with literal-form distractors
  produce the measurable effect (errors are distractor captures — report that rate).
- The probe runner MUST be resumable: key every probe by a stable id, write raw
  outputs one file per probe, SKIP probes whose output file already exists, and print
  progress (done/total) as it runs. Laps have a hard time cap; a killed probe run may
  only cost the unfinished probes — never a restart from zero.
- Seed ONLY with stable values (explicit integers, zlib.crc32) — NEVER Python hash(),
  which is salted per process and will fail the clean-room re-run as non-determinism.
- NEVER delete raw model outputs to pass a gate. A partial grid is legitimate
  work-in-progress: mark it incomplete in the manifest, have run_all.py aggregate
  only finished cells, and let the next lap resume it. Deleting paid-for inference to
  look finished is the expensive kind of tidy — rehearsal burned two batches
  (40+ minutes) this way in one run.
- Place distractors at positions independent of the needle position, or the position
  effect (RQ2) is confounded with distractor placement.
- POSITION MUST BE PAIRED: generate a scenario family (answer code, distractor code,
  filler, and question) without using target position in its seed, then render that same
  family with the target at start, middle, and end. Report paired changes. Rehearsal v13
  used position-specific scenarios, so its strong position gradient was descriptive but
  not a valid clause-reordering test. Do not repeat that design.
- QUALITY MUST BE MATCHED: compare relevant and irrelevant filler only within cases matched
  on measured tier, target position, and question wording. Keep the two filler groups
  balanced inside every tier used for RQ3; never pool extra high-tier relevant probes into
  only one side of the contrast.
- MITIGATION MUST BE MATCHED: compute every pruning gain over the exact scenarios having
  both full-context and pruned outputs. Report paired wins, paired losses, and the matched
  denominator. Never subtract accuracies with different denominators, as rehearsal v13 did.
- Report exact-output compliance and invalid/extra-token output rates alongside accuracy.
  The paper must name the exact GGUF filename and its SHA-256, not just the model family.

## Paper requirements

- ICML LaTeX template, 2–4 pages (HOST RULE, confirmed 2026-07-10 — short papers are
  the format; density is not the goal, selection is): Abstract, Introduction, Related
  Work (brief), Method, Results
  (≥2 figures or tables), Limitations, Reproducibility Statement.
- Honest framing: this is a small-scale replication (lost-in-the-middle, input-length
  degradation — see exemplars) + extension (the context-QUALITY axis, RQ3, and the
  mitigation comparison, RQ4, on a laptop-scale open model). Say so. Overclaiming will
  be rejected by the adversarial reviewer.
- MOTIVATING EXAMPLE: frame the paper with ONE restrained plain-language example —
  asking a question about a single clause buried in a long contract. Introduce it in
  the introduction, use it later only when it clarifies a result, and state explicitly that
  the probes are a synthetic, gradeable version of that situation — never imply real
  contracts were tested. One example used consistently; do not scatter new analogies.
- THE OPENING IS A SCENE, NOT A SUMMARY: the introduction's first paragraph must
  describe a moment the reader has lived, in second person if that helps ("You paste
  a 50-page contract into a chatbot and ask..."), with concrete specifics (a page
  number, a question in quotes) and ZERO terminology. Every actor (the look-alike
  decoy sentence, the model's habit of word-matching) is SHOWN in the scene before
  any section names or defines it. Test: a reader who has only used a chatbot once
  should recognize the situation by sentence two. This standard applies to the
  opening. End the scene after at most two sentences; methods and results use a conventional
  professional research register.
- PROSE STYLE (gate-enforced by harness/gates/check_style.py — violations fail the
  lap): NO em dashes of any kind (no ---, no U+2014/U+2013; rewrite with a comma,
  period, or parentheses; ASCII -- only inside numeric ranges like 1980--84), and
  NONE of the banned filler vocabulary (delve, leverage, crucial, pivotal, moreover,
  furthermore, comprehensive, landscape, showcase, foster, tapestry, paradigm,
  "it is important to note", and similar — the gate prints the full list on failure).
  Plain words beat impressive ones. Professional tone comes from precision, not
  vocabulary.
- PROFESSIONAL REGISTER: write for a technically literate reader outside this narrow
  subfield, not for a child and not for a marketing audience. Use normal research words
  when they are the exact words: estimate, condition, paired comparison, synthetic probe,
  confidence interval. Define specialized ideas once; do not define ordinary words such as
  baseline, mitigation, document, or accuracy. Prefer "synthetic" to "made-up," "estimate"
  to "readout," and "experimental factor" to "knob." First-person plural is allowed and
  often cleaner than repeating "this paper." Never narrate the writing process.

  BAD:  "The target clause is the clause with the correct answer. A mitigation is a cheap
         change meant to reduce errors."
  GOOD: "Each document contains a vendor clause with the correct code and a buyer clause
         with a competing code. We evaluate keyword pruning as a retrieval baseline."

  BAD:  "Table 3 shows the strongest pattern in the current grid. In the contract example,
         the model is most trustworthy when the vendor clause appears first."
  GOOD: "Accuracy fell from \accStart\% to \accEnd\% when the same clause moved from the
         start to the end of the document (Table~\ref{tab:position})."

  Paragraphs should lead with the claim, then evidence, then one necessary qualification.
  Do not alternate every result with a disclaimer; collect secondary caveats in Limitations.
  Avoid three short declarative sentences in a row. Vary sentence openings naturally rather
  than replacing one repeated template with another.
- SENTENCE LAW (the most important paper standard — a paper nobody can follow is a
  failed paper regardless of its numbers). Every sentence must survive four tests,
  each shown with a real failure from rehearsal and its fix:
  1. SIMPLE + EXACT: plain words making a precise claim. If you cannot say exactly
     what a sentence claims, it is broken no matter how simple it sounds.
     BAD:  "Putting more text in a prompt changes more than the amount a model must
           read." (changes more WHAT? the comparison never lands)
     GOOD: "Increasing document length can also change the answer's relative position and
           the number of competing clauses, so an unmatched length comparison does not
           isolate a single cause."
  2. SUBJECTS DO THEIR VERBS: the subject of each sentence must be able to actually
     perform its verb; otherwise the sentence is making something up.
     BAD:  "A longer prompt never changes length alone." (a prompt cannot change
           length — being longer IS the length change)
     GOOD: "We move the same target clause across three positions while holding the
           question, filler, and competing clause fixed."
  3. NOTHING WALKS ON STAGE UNANNOUNCED: no term, name, or shorthand before the
     thing it names has been described in plain words.
     BAD:  "The safe answer should be the clause that governs the vendor." ("safe
           answer" never defined; vendor appears with no setup)
     GOOD: introduce the situation first ("The contract also contains a
           similar-looking clause for the buyer"), then the term may be used.
  4. EVERY KNOB NAMES ITS MACHINE: never bare "length, position, and filler type" —
     always length OF WHAT, with real (macro) values.
     BAD:  "The grid varies length, position, and filler type."
     GOOD: "We vary three properties of each synthetic document: tokenizer-measured length,
           target-clause position, and whether surrounding clauses are topically related."
  Flow: one idea per sentence; a reader meets each concept before it is used; short
  sentences mixed with medium ones. Read every paragraph as if aloud — a stumble is
  a defect to fix, not a style choice.
- THE QUESTIONS ARE VISIBLE: end the Introduction with the paper's questions as a
  short numbered list, in the paper's own plain voice (no "RQ" labels, no spec
  wording), scoped to what was actually measured (use measured macros, not nominal
  sizes) — e.g. "1. As the document grows, how much does accuracy fall?" The Results
  section answers each question by number, with a measured value in the answering
  sentence. A reviewer must find any question and its answer in under a minute.
- READABILITY BAR: a technically literate reader who does not study long-context evaluation
  must follow the argument on one pass. Define specialized statistical terms at first use
  in one precise clause, but assume ordinary research vocabulary. Interpret every table in
  prose without mechanically starting "Table X shows" or repeating the contract example.
  The abstract's last sentence states the takeaway directly. Unexplained jargon is a defect;
  over-explaining ordinary words is also a defect.
- Limitations section must name at least: one small quantized model (findings may not
  transfer to larger models); synthetic probe tasks, not natural documents; retrieval
  accuracy is not general capability; grid size capped by the CPU probe budget (state
  the budget); greedy decoding only (no sampling variance studied).
- Final section before References: a short **Reproducibility** paragraph (3–5 sentences)
  stating that every number in the paper is compiled from analysis scripts in this
  repository, that the data is frozen and checksummed in data/cache/, and that running
  `make all` regenerates every result from the raw data. Reviewers may never see a live
  demo — the paper itself must carry the proof that nothing in it can be faked.

## Rubric (the adversarial reviewer's RUBRIC score /10 follows the competition's
## ICML-style form; the ratchet requires rubric ≥ 6, confirmed by a second read)

- Soundness: method faithfully replicates the cited approach; statistics appropriate;
  paired/matched comparisons are valid; probe counts and uncertainty accompany estimates;
  limitations are real and claims are sized to evidence.
- Presentation: a reviewer can find the question, method, contribution, and headline result
  in 60 seconds; prose is professional; displays are selective and legible.
- Significance: the paper explains who should care, what decision the evidence informs, and
  why the result matters beyond this one synthetic grid without overstating generality.
- Originality: the quality axis, matched mitigation comparison, laptop-scale open-model
  evidence, or an agent-generated finding adds a clear distinction from the cited work.
- Reproducibility supports soundness: a stranger can trace and rerun every reported result.
